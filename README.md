# GigaAM-Diarize: ASR + диаризация через HTTP API

Сервис распознавания речи (GigaAM от Sber) с диаризацией спикеров (pyannote),
завёрнутый в FastAPI и работающий в Docker-контейнере на GPU. Распознавание идёт
асинхронно: запрос создаёт задачу, результат забирается по её id. В комплекте
есть веб-интерфейс: загрузка файла с браузера, расшифровка диалогом по спикерам
и автоматическая суммаризация встречи через LLM
(см. раздел [«Веб-интерфейс»](#веб-интерфейс)).

## Возможности

- `POST /transcribe` — транскрибация аудио (опционально пословные таймстампы).
- `POST /transcribe_diarized` — транскрибация с разделением по спикерам.
- `GET /jobs/{id}` / `DELETE /jobs/{id}` — получение и удаление результата задачи.
- `GET /jobs` — список задач.
- `GET /health` — статус сервиса, версия API, загруженная модель, TTL задач.
- Автоудаление просроченных задач: результаты хранятся только в оперативной памяти
  и удаляются по истечении `JOB_TTL_SECONDS`.

## Требования
- Docker с [NVIDIA Container Toolkit](https://docs.nvidia.com/data-center/cloud-native/container-toolkit/).
- Docker Compose v2.
- Токен Hugging Face с доступом к гейтед-моделям pyannote: `pyannote/speaker-diarization-community-1`
  (модель диаризации по умолчанию) и `pyannote/segmentation-3.0` (VAD). На страницах
  моделей нужно принять условия лицензии (для community-1 — CC-BY-4.0). Получить
  токен: https://huggingface.co/settings/tokens
- Если community-1 недоступна (условия не приняты, нет токена или кэша), сервис
  автоматически переключается на `pyannote/speaker-diarization-3.1` с предупреждением
  в логах. Модель можно задать явно через `PYANNOTE_DIARIZATION_MODEL`.

## Сборка контейнера

1. Создайте файл `.env` в корне репозитория:

   ```env
   HF_TOKEN=hf_xxxxxxxxxxxxxxxxxxxxxxxxxxxx
   # необязательные параметры:
   GIGAAM_MODEL=v3_e2e_rnnt
   API_PORT=8000
   JOB_TTL_SECONDS=1800
   # веб-интерфейс и LLM-суммаризация (необязательно):
   WEBUI_PORT=8001
   OPENROUTER_API_KEY=sk-or-v1-xxxxxxxxxxxxxxxx
   OPENROUTER_MODEL=z-ai/glm-5.3-flash
   ```

2. Соберите образ (compose сам передаст `HF_TOKEN` как build secret):

   ```bash
   docker compose build
   ```

   либо явно:

   ```bash
   docker compose build --secret id=hf_token,env=HF_TOKEN
   ```

   При сборке в контейнер скачивается чекпоинт выбранной модели
   (`prepare_models.py`), поэтому собранный образ работает без интернета.

3. Запустите:

   ```bash
   docker compose up -d
   ```

   Сервис поднимется на `http://localhost:${API_PORT:-8000}`, веб-интерфейс — на
   `http://localhost:${WEBUI_PORT:-8001}`. Готовность:
   `GET /health` (healthcheck в compose опрашивает его каждые 30 секунд).

## Параметры, на которые стоит обратить внимание

| Параметр | Где задаётся | По умолчанию | Описание |
|---|---|---|---|
| `HF_TOKEN` | `.env` (секрет сборки и runtime) | — | Токен HF для гейтед-моделей pyannote. Без него диаризация не сможет скачать модели. |
| `GIGAAM_MODEL` | build ARG + runtime env | `v3_e2e_rnnt` | Какой чекпоинт GigaAM скачать при сборке и загрузить при старте. |
| `API_PORT` | `.env` | `8000` | Порт на хосте, который проксируется на 8000 внутри контейнера. |
| `WEBUI_PORT` | `.env` | `8001` | Порт веб-интерфейса на хосте (контейнер `web`). |
| `JOB_TTL_SECONDS` | runtime env | `1800` | Сколько секунд хранить завершённую задачу, потом автоудаление. `0` — отключить автоудаление. |
| `OPENROUTER_API_KEY` | `.env` | — | Ключ OpenRouter для LLM-суммаризации. Без него `POST /api/summarize` возвращает `503`. Ключ живёт только в контейнере `web` и не попадает в браузер. |
| `OPENROUTER_MODEL` | `.env` | `z-ai/glm-5.3-flash` | Модель LLM по умолчанию; переопределяется полем модели в интерфейсе. |
| `PYANNOTE_DIARIZATION_MODEL` | runtime env | `pyannote/speaker-diarization-community-1` | Какой пайплайн диаризации использовать. Например, `pyannote/speaker-diarization-3.1`, чтобы вернуть прежнюю модель. |
| `PYANNOTE_DIARIZATION_PARAMS` | runtime env | — | JSON с частичным переопределением гиперпараметров пайплайна (`pipeline.instantiate`). Например: `{"clustering": {"threshold": 0.6, "Fa": 0.07, "Fb": 0.8}}`. Не указывайте параметры, которых нет у активного пайплайна. |

Доступные варианты `GIGAAM_MODEL`: `v1_ctc`, `v1_rnnt`, `v2_ctc`, `v2_rnnt`,
`v3_ctc`, `v3_rnnt`, `v3_e2e_ctc`, `v3_e2e_rnnt`, `multilingual_ctc`,
`multilingual_large_ctc`. Для API по умолчанию рекомендуются `v3_e2e_rnnt`
(лучшее качество) или `v3_e2e_ctc` (быстрее, проще постобработка). При смене
модели не забудьте пересобрать образ — чекпоинт запекается на этапе сборки.

### Модель диаризации

По умолчанию используется [`pyannote/speaker-diarization-community-1`](https://huggingface.co/pyannote/speaker-diarization-community-1)
(требует `pyannote.audio >= 4.0` — в `pyproject.toml` уже пинится `4.0.*`):
powerset-сегментация, кластеризация VBx и PLDA-рескоринг. У неё другая схема
гиперпараметров, чем у 3.1: у кластеризатора VBx это `threshold`, `Fa`, `Fb`
(у агломеративной кластеризации 3.1 — `min_cluster_size` и `threshold`), а у
сегментации — только `min_duration_off`. Параметры из конфига модели уже
настроены авторами pyannote, поэтому по умолчанию ничего переопределять не нужно.

Лицензии: код GigaAM — MIT (Sber, https://github.com/salute-developers/GigaAM),
код пайплайнов pyannote — MIT, а веса модели `speaker-diarization-community-1`
распространяются по CC-BY-4.0 (у 3.1 — MIT). При использовании результатов
и распространении проекта указывайте авторство pyannote.

## Веб-интерфейс

Вместе с API поднимается лёгкий контейнер `web` (без GPU): статический UI и
прокси к API. Браузер ходит только на `http://localhost:${WEBUI_PORT:-8001}`,
все запросы к API идут с того же origin — CORS не нужен, а секреты не попадают
в браузер.

- **Загрузка файла.** Подходит любой аудио/видеофайл, который понимает ffmpeg.
  Перед отправкой в API веб-контейнер нормализует файл в WAV 16 кГц моно.
  Это обходит ошибку pyannote 4.0.7 + torchcodec с edit-list у некоторых MP4
  («получила N сэмплов вместо ожидаемых M» при прямом POST на порт API) —
  через интерфейс такие файлы распознаются корректно.
- **Ход задачи.** Статус опрашивается автоматически; после завершения
  расшифровка показывается диалогом с репликами спикеров (`SPEAKER_01`, …)
  и пословными таймстампами.
- **Список задач.** Последние задачи доступны в панели; при перезагрузке
  страницы восстанавливается последняя задача.
- **Суммаризация встречи через LLM.** После завершения диаризации расшифровка
  автоматически уходит в OpenRouter (`POST /api/summarize`):
  - системный промт редактируется в сворачиваемой панели;
  - модель задаётся полем в интерфейсе (по умолчанию `z-ai/glm-5.3-flash`,
    подойдёт любая модель, доступная вашему ключу OpenRouter);
  - резюме рендерится как Markdown (заголовки, списки, таблицы, код), кнопка
    «Копировать резюме» кладёт в буфер исходный Markdown;
  - кнопка «Суммаризовать заново» повторяет запрос (расход токенов).
- **Без повторных списаний.** Промт, модель и резюме хранятся в `localStorage`
  по `job_id`: открытие задачи из списка или перезагрузка страницы не вызывают
  LLM повторно.

Запрос в LLM идёт по цепочке «браузер → контейнер `web` → OpenRouter»:
ключ `OPENROUTER_API_KEY` задаётся в `.env` и живёт только в переменных
окружения контейнера. Без ключа `POST /api/summarize` возвращает `503`,
при ошибке OpenRouter — `502`. Прокси также оборачивает методы API:
`/api/transcribe`, `/api/transcribe_diarized`, `/api/health`, `/api/jobs`
(список, получение и удаление задачи).

После правок в `web/` достаточно пересобрать только его:

```bash
docker compose build web && docker compose up -d --no-deps web
```

## Примеры использования

Транскрибация:

```bash
curl -s -X POST "http://localhost:8000/transcribe" -F "file=@audio.wav" \
  | jq '{job_id, status}'
```

Диаризация с фиксированным числом спикеров и пословными таймстампами:

```bash
curl -s -X POST "http://localhost:8000/transcribe_diarized" \
  -F "file=@audio.wav" -F "num_speakers=2" \
  | jq '{job_id, status}'
```

Получение результата (повторять, пока `status != "completed"`):

```bash
curl -s http://localhost:8000/jobs/<job_id> | jq
```

Только один запрос распознаётся одновременно: если модель занята, второй POST
вернёт `409 Conflict`. Очередь не копится — повторите запрос позже.

> **Примечание.** Некоторые MP4 при прямом POST на порт API могут падать
> с ошибкой edit-list torchcodec. Веб-интерфейс нормализует все файлы через
> ffmpeg перед отправкой, поэтому через него такие файлы работают.
